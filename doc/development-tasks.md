## 1. 执行约定

任务按依赖推进，每个任务交付可独立检查的实现和证据，通常对应一个有明确边界的 PR。尚未建立产品工具链，文中代码路径为拟建路径；HB-09 落地目录与 README 命令后，后续任务使用真实命令，不把这里的路径当成现有模块。

“负责人”表示所需职责，尚未分配具体人员。原型中的模拟状态不能作为任何产品任务的验收证据。可行性任务可以失败，但失败必须给出实际版本、复现过程与调整结论，不能标成产品能力通过。原定基线冻结后才能执行依赖该基线的正式任务；用户最新授权先推进 HB-07 之后的候选契约与实现，不等待 HB-04 至 HB-07 全部收尾。此例外仅解除开工顺序，不解除真实验收、版本冻结和普通用户启用门槛，依赖验收不得因此标完成。

通用完成标准：范围内代码与配置已实现；成功和主要失败行为可复现；运行过的命令、版本、预期/实际、脱敏证据写入对应 `doc/verification/HB-xx.md`；更新必要文档；无未解释的敏感数据、模拟替代或未授权旁路。实际调用密钥通过既定安全渠道注入，不进夹具和报告。

排期在 HB-08 完成后按真实适配成本和团队人数估算，不沿用两天目标。三种外部 harness、本地及联网路径、MCP、CLI 均在本期，探针失败只能调整版本、方案或周期。

## 4. 检查任务图与需求覆盖

从仓库根目录运行 `python3 scripts/check-development-plan.py`。脚本从任务卡读取依赖和需求编号，检查 ID 唯一、前置存在、无环、元数据完整，以及 PRD 全部 F/S 编号均有落点；输出可开工任务和依赖层次。

结构覆盖只说明计划有对应任务，不能证明该任务设计充分或实现通过。未来更新任务状态必须依据真实交付物与证据。产品实现命令由 HB-09 建立，本脚本只检查文档计划。
