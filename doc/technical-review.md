# Havenbox MVP 方案复审

日期：2026-10-25

评审基线：PRD V0.5、技术方案 V0.2、原 HB-01 至 HB-34 计划和当前工作区候选实现。

结果：采用 [PRD V0.6](./product-requirements.md)、[技术方案 V0.3](./technical-design.md) 和 [MVP 执行计划 V0.2](./development-tasks.md)。

## 1. 结论

V0.5 是完整内部产品版，不是最小可用产品。它同时要求三种外部 harness、本地与联网模型、MCP 和 CLI、多会话及恢复。这些能力形成 34 个任务和多个组合验收，推迟了第一条真实用户链路。

V0.6 把 MVP 收窄为一个内置 Agent、一个联网模型组合和一个 CSV CLI。MVP 保留 VM 隔离、文件边界、凭据代理、数据披露、计划审批、确定性执行、停止和安全导出。

## 2. 主要发现

### 2.1 计划先证明扩展性，后证明产品价值

旧计划直到 HB-31 才要求完整组合验收。VM、网关、外部 harness、MCP、恢复和 UI 在此之前分别开发。任何接口不匹配都可能在后期阻断整条链路。

新计划要求 MVP-02 至 MVP-04 先完成无界面端到端任务。UI 只建立在真实模型、真实 VM、真实 CLI 和真实成果提交之上。

### 2.2 外部 harness 增加了不必要的首版变量

Kimi CLI、Pi 和 dsh 使用不同协议、配置、工具桥、会话和取消机制。每种 harness 还需要证明没有隐藏模型请求、旁路工具和旧权限恢复。

这些工作验证平台兼容性，但不验证用户是否需要 Havenbox。MVP 使用内置 Agent，先证明隔离工作空间和 CSV 任务流程。

### 2.3 双推理路径扩大了交付条件

旧范围同时要求本地模型和联网模型。本地路径依赖模型资产、GPU、模板、许可证、内存和物理断网验收。联网路径依赖 Keychain、网关、端点和数据授权。

当前仓库已有联网配置和 Keychain 候选。本地模型仍缺真实资产和 GPU 验收。MVP 因此选择一个冻结的联网组合。本地路径列入下一版本。

### 2.4 MCP 与 CLI 重复验证同一工具价值

CSV 引擎已经提供确定性能力。旧方案要求同一能力同时经 MCP 和 CLI 调用，再比较结果和停止行为。

MVP 只保留 CLI，因为仓库已有 `CallPermit` 候选。MCP 在核心链路稳定后再接入。

### 2.5 多会话恢复不是首次任务的前置条件

搜索、归档、跨会话引用、原生 harness 恢复和摘要重建需要复杂的数据生命周期。首次用户任务只需要保存审批、调用和成果，并在重启后避免重放。

MVP 只提供一个工作空间和一个活动任务。历史只读。未完成任务重启后标记中断。

### 2.6 原计划状态与仓库事实不一致

旧计划仍把多个任务标为未开始，但仓库已有以下候选：

- HB-10 存储和事务。
- HB-11 真实 VM 与 Supervisor 路径。
- HB-13 CSV 引擎。
- HB-14 CLI 与 `CallPermit`。
- HB-16 配置与 Keychain。

新计划把这些成果列为候选输入，不把它们直接标为 MVP 完成。每项仍需进入同一个真实端到端组合。

## 3. MVP 范围决定

| 能力 | 决定 | 说明 |
| --- | --- | --- |
| 内置 Agent | 保留 | 最短路径，可完全控制上下文和工具调用 |
| 一个联网模型 | 保留 | 复用现有配置和 Keychain 候选 |
| QEMU/HVF VM | 保留 | 产品安全价值的基础 |
| CSV 引擎与 CLI | 保留 | 已有候选实现，能产生可检查结果 |
| 数据披露和计划审批 | 保留 | 分别控制联网和文件执行 |
| 停止、重启核查和安全导出 | 保留 | 防止后台执行、重放和宿主文件误写 |
| Kimi CLI、Pi、dsh | 延后 | 三套适配协议不影响 MVP 假设 |
| 本地模型 | 延后 | 资产、GPU、内存和离线验收尚未闭环 |
| MCP | 延后 | 与 CLI 重复验证工具能力 |
| 多会话和原生恢复 | 延后 | 增加数据生命周期和权限恢复成本 |
| 自定义端点和多提供方 | 延后 | 扩大 SSRF、协议和配置验证范围 |

## 4. 不可削减的安全要求

MVP 缩小产品能力，不缩小以下边界：

- 来宾无直接网络和宿主目录共享。
- 文件只经受控导入、只读输入、成果校验和显式导出跨界。
- 上游 Key 只存在于宿主 Keychain 和发送请求的进程。
- 模型请求绑定任务、模型、数据范围、期限和预算。
- 工具调用绑定已批准计划、固定 executable、参数、输入和输出。
- 停止、退出、超时和失联必须清理全部受管进程。
- 恢复不自动重发请求或工具调用。
- 失败、部分结果和结果未知不能显示为成功。

## 5. 计划变化

新计划使用 8 个任务取代原 34 个任务：

1. 冻结唯一组合和验收入口。
2. 完成文件边界与真实 VM 任务通道。
3. 完成真实 CSV CLI 成果链。
4. 完成推理、披露与内置 Agent。
5. 实现桌面主流程。
6. 完成停止、恢复与诊断。
7. 完成安全与故障验收。
8. 制作内部包并完成用户验收。

任务按用户链路组织，不按组件列表组织。每个实现阶段都以可运行行为结束。

## 6. 验收变化

旧验收要求多个 harness、两种推理路径和 MCP、CLI 双入口。新验收只针对一个冻结组合，但要求该组合完成以下真实行为：

- 一个真实模型生成声明式计划。
- 一个真实 VM 中的 CLI 处理固定 CSV。
- 实际模型出口与用户批准内容一致。
- 来宾没有宿主文件、网络和凭据访问权。
- 停止和崩溃后没有任务进程。
- 用户无需终端完成导入、确认、执行、预览和导出。

三个目标用户仍是交付门槛。用户试用用于验证产品流程，不替代安全测试。

## 7. 后续扩展顺序

MVP 通过后，下一版本先增加本地模型。该步骤验证离线价值主张。随后增加一个外部 harness，再增加 MCP 和多会话。每项能力都复用已经通过的宿主边界，不同时引入多套新协议。

## 8. 本次验证范围

本次工作只复审和更新文档、任务图与静态检查规则。旧验证记录和现有候选代码未被删除。本次没有运行真实模型、VM、CLI 或 UI 产品流程，因此没有新增产品行为验收结论。
