# HB-02 VM 建设与验证证据

日期：2026-10-24
工作区：`feat-hb-01-lock`  依据：origin/main `AGENTS.md`、PRD S01/S02/S03/S07/S11、`doc/development-tasks.md` HB-02。

## 结果

**blocked / 未通过真实 VM 验收。** 本机确认 macOS arm64 与 HVF 支持，但没有可运行的 `qemu-system-aarch64`、`qemu-img`，也没有经过校验的 ARM64 guest image、kernel、initramfs 或可执行 guest payload，因此不能实际启动 smoke VM，也不能声称无网卡、无共享目录、无 QMP、重启持久性和 guest-side 探针通过。

已准备可复现资产编排与生命周期入口：

- `experiments/vm/prepare.sh`：调用 `qemu-img create -f raw` 创建持久数据盘，校验输入为普通非符号链接文件，并生成 `asset-manifest.json`（大小、SHA-256、绝对路径）。
- `experiments/vm/start.sh` / `stop.sh` / `clean.sh`：启动、停止、清理 QEMU runtime state；清理不删除 guest source artifacts。
- `experiments/vm/guest-payload.sh`：记录 fw_cfg `opt/havenbox.payload` 的 guest-side payload 合约；它不是 bootable kernel/initramfs，不能替代 guest 实现。
- `experiments/vm/probe.py`：固定 ARM64 `virt`、HVF、`cpu host`、只读 root image、持久 raw virtio 数据盘、无网络/QMP/共享目录的命令及边界校验。

## Review 二次修复证据

`start.sh` 已设为可执行（文件模式 0755），直接调用已实测。已移除“创建 QEMU 后立即输出本地 token 即代表 ready”的逻辑：启动通过 `fw_cfg opt/havenbox.nonce` 传入随机 nonce，只有 QEMU 串口 stdout 返回完整 `HB02_GUEST_READY <nonce>` 行且 QEMU 仍存活，才生成宿主内部 readiness 记录，随后生命周期层才写 pidfile 和输出成功。stderr 不参与握手，串口与 stderr 均加来源前缀，不能伪造宿主内部 READY 行。退出、错误握手与超时均非零退出并清理进程组；超时默认 30 秒，可通过 `HB02_START_TIMEOUT` 设置到最多 300 秒。

真实 guest 必须在初始化完成后读取 nonce 并从串口发回该行；仓库现有 payload 只声明合约，没有实现此流程。二次检查 `command -v qemu-system-aarch64` 与 `command -v qemu-img` 均未找到工具，真实 guest handshake、设备隔离和持久性继续 **blocked / unverified**。

## 下一步命令

在 arm64 Homebrew 或可复现源码构建环境完成工具安装后，先记录：

```sh
brew install qemu
qemu-system-aarch64 --version
qemu-img --version
```

再提供真实、可校验、许可明确的 ARM64 guest artifacts，并执行：

```sh
experiments/vm/prepare.sh --image path/to/guest.raw --kernel path/to/Image --initrd path/to/initramfs --payload path/to/payload.sh
experiments/vm/start.sh --image path/to/guest.raw --data experiments/vm/state/data.raw --kernel path/to/Image --initrd path/to/initramfs --payload path/to/payload.sh
```

必须从 guest 串口输出记录设备/挂载、`ip link`（无网络）、QMP/共享目录不可达、宿主文件/互联网/局域网不可访问，并写入数据盘对象后重启，比较重启前后 SHA-256；任何一项未执行都保持 blocked/unknown。
