# HB-02 VM probe

`run.sh self-test` executes bounded frame checks plus a real OS pipe test. It verifies unknown kinds, stale epochs, truncated/oversized frames, invalid control actions, negative and boolean offsets, empty/oversized transfer IDs, cancellation frames, cancelled transfers, and cancellation of a blocked read. Its JSON result explicitly says `vm_boundary: unverified`.

`prepare.sh` creates a persistent raw data disk through `qemu-img create`, then writes `asset-manifest.json` with byte sizes and SHA-256 values for the read-only image, kernel, initramfs, guest payload, and data disk. `start.sh`, `stop.sh`, and `clean.sh` provide repeatable lifecycle operations; `clean.sh` removes only runtime state and never source guest artifacts. The checked-in `guest-payload.sh` is a minimal fw_cfg payload contract and does not claim to be a bootable Linux guest.

`run.sh launch` requires all of `--image`, `--data`, `--kernel`, `--initrd`, and `--payload`. Image/data/payload/kernel/initramfs must be regular non-symlink files with bounded sizes; the image uses a `.raw` or `.img` suffix and the data disk has a minimum capacity. Memory is limited to 128M..8192M, CPUs to 1..8. Missing or invalid inputs, QEMU, or a failed QEMU version probe return `blocked` (exit 3).

The launch path requires a real ARM64 kernel/initramfs and guest payload. Startup sends a fresh nonce through `fw_cfg` key `opt/havenbox.nonce`; guest initialization must read that key and emit exactly `HB02_GUEST_READY <nonce>\n` on its serial stdout only after its initialization is ready. The host checks the complete line and QEMU liveness before emitting its internal readiness record; only then does `start.sh` write the pidfile and announce success. Serial and diagnostic output are prefixed so they cannot impersonate that internal record. Exit, malformed handshake, or `HB02_START_TIMEOUT` (default 30 seconds, maximum 300) cleans up the process group and fails closed. The supplied payload does not implement this guest initialization, so real startup remains unverified and cannot succeed merely by creating a QEMU process.

`python3 experiments/vm/test_lifecycle.py` exercises host startup with explicitly fake QEMU fixtures, including immediate exit, timeout, wrong nonce, forged readiness on stdout/stderr, handshake followed by exit, successful serial response, stale PID protection, symlink state rejection, and preservation of assets after cleanup. These tests are not guest or VM boundary evidence.

The launch path uses `virt`, `hvf`, `cpu host`, `-nodefaults`, serial stdio, a read-only root image, a writable persistent raw virtio disk, and an explicit `fw_cfg` payload. It has no `-nic`, `-netdev`, QMP, shared folders, or host directory mounts. This script does not claim guest isolation or VM success: those require running QEMU with real artifacts and recording guest probe output, device/mount/network checks, and reboot persistence.
